# `@study-feed/core`: dominio

Il core contiene le regole dell'app in TypeScript puro ([ADR 0004](../decisions/0004-clean-architecture-e-qualita.md)): nessun framework, nessun accesso a rete o database. Gira uguale nel browser, in Node, nelle funzioni edge e nel server MCP, e si testa senza simulare nulla.

```
packages/core/src/
├─ domain/
│  ├─ ids.ts              id "marchiati" (LessonId, LessonPartId…) e parseId
│  ├─ errors.ts           DomainError con codici stabili
│  ├─ text.ts             normalizzazione dei testi
│  ├─ catalog.ts          Source, Lesson, LessonPart
│  ├─ content.ts          contenuto di una parte e forma canonica
│  ├─ content-hash.ts     impronta SHA-256 del contenuto
│  ├─ content-version.ts  ContentVersion e stati di generazione
│  ├─ entitlement.ts      Entitlement e prova di possesso
│  ├─ subtitles.ts        tracce di sottotitoli, forma canonica e impronta
│  └─ import.ts           lezione importata: percorso nel catalogo, parti, validazione
└─ application/
   ├─ ports.ts                     porte: Clock, IdGenerator, CatalogRepository, EntitlementVerifier
   ├─ possession-proof-verifier.ts verifica per prova di possesso
   └─ import-lesson.ts             caso d'uso ImportLesson
```

## Entità
| Entità | Cosa rappresenta |
|---|---|
| `Source` | Una fonte di studio: lezione Epicode o libro personale (i libri arrivano in M7) |
| `Lesson` | Lezione del catalogo condiviso (Directus `activity`), solo metadati |
| `LessonPart` | Parte di una lezione, `video` o `reading`: l'unità su cui si concedono i permessi |
| `ContentVersion` | Revisione datata del contenuto di una parte, identificata dall'impronta |
| `Entitlement` | Permesso di uno studente su una versione |
| `SubtitleTrack` | Traccia di sottotitoli di una parte video, in una lingua, separata dalle versioni |

Gli id sono tipi "marchiati": a runtime sono stringhe UUID, ma il compilatore impedisce di passare un `LessonId` dove serve un `LessonPartId`. Le funzioni `create*` validano e normalizzano i campi e restituiscono oggetti congelati.

## Contenuto, forma canonica e impronta
Il contenuto importato di una parte è:
- `video`: riassunti `it`/`en` (fonte principale); i sottotitoli **non** fanno parte del contenuto ma sono tracce separate (vedi sotto, [ADR 0009](../decisions/0009-import-lezione-intera-e-sottotitoli.md));
- `reading`: un testo markdown (per esempio il riassunto di capitolo).

`normalizeContent` lo porta in **forma canonica**, in modo che due import dello stesso materiale siano identici byte per byte:
- testi in Unicode NFC, fine riga `\n`, niente spazi in coda, al massimo una riga vuota di fila (l'indentazione resta, perché nel codice conta);
- riassunti vuoti rimossi (una parte video può restare senza riassunti se ha sottotitoli);
- limite di sicurezza: 200 000 caratteri per testo.

`computeContentHash` serializza la forma canonica in JSON con le chiavi ordinate (`canonicalJson`), la codifica in UTF-8 e ne calcola lo SHA-256 con la Web Crypto API (iniettabile per i test). Risultato: 64 caratteri esadecimali.

Perché conta: lo stesso contenuto importato da più studenti si salva **una volta sola**, e se Epicode modifica una lezione l'impronta cambia e nasce una **nuova versione** ([ADR 0002](../decisions/0002-contenuti-condivisi-con-prova-di-accesso.md)).

## Sottotitoli
Una `SubtitleTrack` ha lingua (`it`, `en-x-autogen`…, formato BCP 47 semplificato), `autoGenerated` e le righe (`startMs`, `endMs`, `text`). `normalizeSubtitleTrack` la porta in forma canonica: righe ordinate per tempo, righe vuote scartate, a capo interni uniti, tempi interi e coerenti, al massimo 10 000 righe; una traccia vuota è rifiutata. `computeSubtitleTrackHash` ne calcola l'impronta come per il contenuto.

Le tracce sono separate dalle versioni per due motivi ([ADR 0006](../decisions/0006-sottotitoli-come-fonte-secondaria.md), [ADR 0009](../decisions/0009-import-lezione-intera-e-sottotitoli.md)): i sottotitoli auto-generati cambiano più spesso dei riassunti e non devono far nascere versioni nuove (e rigenerare le schede), e una traccia si può aggiungere o mancare senza toccare il contenuto principale. Anche le tracce si deduplicano per impronta e si concedono per prova di possesso.

## Import di una lezione
`normalizeLessonImport` valida la lezione che arriva dall'estensione: percorso nel catalogo (corso di studi, edizione, materia, capitolo, lezione), da 1 a 40 parti senza id Epicode ripetuti, tipo della parte coerente con il contenuto, id del video solo per le parti video, al massimo 4 tracce con lingue diverse, e scarta le parti video senza riassunti né sottotitoli. Le parti escono ordinate per posizione.

`ImportLesson.execute(userId, lezione)`:
1. normalizza e calcola le impronte di contenuti e tracce **prima** della transazione;
2. dentro `CatalogRepository.transaction`: `upsertLessonPath`, `upsertLessonPart`, `findOrCreateVersion`, `EntitlementVerifier.verify` (oggi `PossessionProofVerifier`, che ricalcola l'impronta e chiama `grantByPossessionProof`), `saveEntitlement`; per ogni traccia `findOrCreateSubtitleTrack` e `saveSubtitleAccess`;
3. restituisce per ogni parte gli id e se versione, permesso e tracce sono nuovi.

Le porte di persistenza (`CatalogRepository`, `CatalogTransaction`) sono implementate in `packages/adapters` con Drizzle; il caso d'uso si testa con un catalogo in memoria. Passare alla verifica ufficiale Epicode vorrà dire scrivere un altro `EntitlementVerifier`.

## Stati di generazione
Le schede le genera Claude Desktop tramite il server MCP ([ADR 0007](../decisions/0007-generazione-via-mcp-e-login.md)). Ogni versione ha uno stato:

```
pending ──▶ generating ──▶ ready (finale)
               │  ▲  │
               │  │  └──▶ failed ──▶ generating
               └──┴──▶ pending   (generazione abbandonata)
```

`ready` è finale: il risultato si accetta una volta sola per versione; le correzioni passano da una nuova versione o da "Segnala errore". `transitionGeneration` rifiuta le transizioni non ammesse con `INVALID_STATUS_TRANSITION`.

## Feed di una lezione e allineamento al minuto
`feed.ts` definisce schede, quiz, concetti e glossario bilingui (`Bilingual<T>`), `checkLessonFeed` (regole tra elementi, restituisce tutti i problemi) e `computeLessonSourcesHash` (impronta delle fonti di una lezione). `alignment.ts` calcola il tratto di video di una scheda dai sottotitoli (`alignCard`), in modo deterministico. Dettagli in [generation.md](generation.md).

## Feed di studio
Regole pure del feed sul telefono ([ADR 0015](../decisions/0015-feed-di-studio-m3.md)), in `domain/story.ts` e `domain/study-session.ts`; lavorano su tipi strutturali (`StoryCardInput`, `SequenceLessonInput`) così valgono sia per i documenti salvati sia per i dati dell'API.

- `storyOf(card, lingua)` → `CardStory`: battute (`title`, `key`, poi `line`/`step`/`row`/`note`/`code` secondo il tipo), parola da indovinare, righe del confronto, codice con le spiegazioni. `beatText` dà il testo di una battuta (sintesi vocale, avanzamento automatico), `autoAdvanceMs` il tempo di lettura (55 ms a carattere, almeno 2,2 s).
- `splitSentences`: frasi chiuse da `. ! ? ; :` seguiti da maiuscola, cifra o apertura; non spezza decimali, `cursor.next`, abbreviazioni (`es.`, `e.g.`) e unisce i pezzi sotto 32 caratteri.
- `pickBlank(fraseChiave, termini)`: il termine più lungo che compare come parola intera (senza maiuscole), poi una complessità `O(...)`, un identificatore con il punto (`cur.next`), un numero di almeno due cifre; mai oltre il 60% della frase.
- `highlightTerms`: pezzi del testo con i termini evidenziati, senza sovrapposizioni.
- `codeBlocks` e `pairCodeExplanation`: blocchi separati da righe vuote; ogni frase illumina il blocco (o i blocchi a pari merito) con più identificatori in comune, o, con un solo blocco, le righe che li contengono; nessun identificatore in comune → nessuna evidenza.
- `buildStudySequence(lezioni)`: schede in ordine e, ogni `QUIZ_EVERY` (3) schede, un gruppo di al massimo `QUIZ_BATCH` (3) domande della stessa lezione: prima sui concetti delle ultime schede, poi sugli altri già visti nella lezione, mai su concetti non ancora visti; un gruppo finale se dopo l'ultimo c'è almeno una scheda. Ogni domanda porta `batch` (`position`, `size`) per mostrare *1/3*.
- `POINTS`, `answerPoints(serie)` (10 + 2 per risposta giusta di fila oltre la prima, al massimo +8) e `SESSION_MS` (5 minuti).

## Ripasso
`domain/review.ts` e `application/review.ts` (M4, [ADR 0017](../decisions/0017-ripasso-ed-esame-m4.md)):
- `ConceptReviewState`: stato FSRS di un concetto (`conceptId` = `materia:chiave`), con date ISO 8601 per IndexedDB e sincronizzazione; `applyReview` lo aggiorna con `ts-fsrs` (parametri predefiniti, `enable_fuzz: false`, date precedenti all'ultima risposta portate all'ultima); `isDue`, `isStable` (fase di ripasso e stabilità ≥ 7 giorni), `recallProbability`.
- `gradeFromAnswer` (sbagliata → *again*, aiutata → *hard*, giusta → *good*) e `gradeFromScore` (soglie 50% e 80% dell'ADR 0014).
- Serie di giorni: `extendDayStreak`, `currentDayStreak`, `localDay` (giorno nell'ora del dispositivo).
- Porta `ProgressStore` e casi d'uso `recordAnswer` (stato + storico con fonte e lingua), `completeReviewSession` (serie), `planReviewSession` (fino a 10 concetti: scaduti dal più in ritardo, altrimenti in anticipo i meno ricordati; mai concetti non ancora visti o senza domande; domanda successiva all'ultima fatta, a giro), `summarizeReview` (scaduti, deboli, avanzamento per modulo).

## Prova di possesso
`grantByPossessionProof(user, version, presentedHash, now)` concede il permesso solo se l'impronta del contenuto presentato coincide con quella della versione. L'impronta va calcolata **dal server** sul contenuto ricevuto, mai presa dal client: non basta dichiarare di avere una lezione, bisogna inviarne il contenuto.

## Errori
`DomainError` ha un `code` stabile (`INVALID_ID`, `INVALID_CONTENT`, `ENTITLEMENT_MISMATCH`…) che l'API tradurrà in risposte HTTP e la UI in messaggi, senza dipendere dal testo.

## Test
Vitest, un file di test per modulo, con soglie di copertura (95% righe/funzioni, 90% rami) che fanno fallire la CI se scendono. Oggi la copertura è al 100% delle righe.
